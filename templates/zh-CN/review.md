# 验收：<标题>

> 字段名、状态值和文件名保持英文；正文用中文。

## Review kind（验收类型）

`self` 或 `independent`。

`self` 表示这次变更的设计或实现也是你做的。直说即可：标注清楚的自审是有价值的，
不标注的自审是误导。

## Acceptance item results（验收项结果）

| # | Criterion | Result |
|---|---|---|
| AC1 | | pass / fail / unverified |
| AC2 | | |

每条标准只有一个结果。没有第四个取值：不是 `partial`，不是 `mostly`，不是 `n/a`。
实现者没有尝试的标准是 `fail`——`unverified` 说的是你有没有能力核实，不是他们有没有
选择去做。

## Evidence（证据）

| # | 你怎么核实的 | 你观察到什么 |
|---|---|---|
| AC1 | | |

来自你在本次验收中打开的文件或运行的命令。实现报告是「去哪里看」，不是「你看到了
什么」。

如果某条标准在一个你已知是错的实现下会给出同样的结果，在这里说明。它通过了，但没
有区分出任何东西。

## Deviation decisions（偏离处置）

| Deviation | Accepted? | 原因 |
|---|---|---|
| | | |

实现者记录的每一处偏离一行。如果产物里有他们没记录的偏离，补进来并注明是未申报的。

## Artifact integrity（产物完整性）

与代码分开，单说产物本身的状态。

设计中记为「用户原话」的那段文本是否完好——格式正常、没有被截断、没有被复述？
那里的损坏会阻塞，即使每条验收标准都通过：它是「这个决定出自用户」的唯一证据。

你注意到的其他问题——失效的交叉引用、两节互相矛盾、实现报告里被证伪的说法——
都写在这里作为发现，本身不构成阻塞。

## Blocking fixes（阻塞修复项）

在这次变更算完成之前必须改的东西。每一条都点名标准、实测结果、以及要变成什么样。

## Non-blocking suggestions（非阻塞建议）

你想改但不因此卡住的东西。单独成列，让读者能分清哪一列是必须处理的。

## Final status（最终状态）

`rework` 或 `complete`，以及理由。阻塞修复项里还有内容时，不要写 `complete`。
